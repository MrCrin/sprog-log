# Nap and night display mode

**Implementation branch:** `feat/nap-night-display-mode`. The implementing agent should use this branch if permitted by its environment; if branch switching is prohibited, retain the session branch and report the restriction. Do not change branches during planning.

## Decisions and rationale

- Keep the existing start/stop logging mechanism and sleep timestamps unchanged. Classification and grouping are presentation semantics, reversible by disabling the mode; no estimates or inferred actual sleep totals.
- Settings: mode on/off, effective local date, bedtime (default 19:00) and wake-up (default 07:00). Existing sleep-day-start remains independent and controls chart wrapping and display-day bucketing only. Unset times use defaults; reject equal bedtime and wake-up. Current settings apply retroactively; no settings history.
- Enable the new view from the selected local date inclusive; earlier dates retain the current view. For nights, the date is the morning date of the assigned night window. Turning mode off restores the current view everywhere without deleting overrides or settings.
- Classify each entire interval by actual elapsed time overlapping recurring local night windows versus daytime; more than half at night means Overnight, otherwise Nap (ties are Nap). Do not use sleep-day-start for classification. Respect timezone and daylight-saving transitions.
- Per-entry edit offers Auto, Nap, Overnight. Auto dynamically follows interval and current settings; forced choices persist until changed or reset to Auto. This requires persisted metadata, but never modifies start/end data. Handle active entries without disrupting existing start/stop behavior.
- Assign Overnight entries to the night window with the greatest elapsed overlap; for a forced entry without overlap, choose the nearest window, breaking ties toward the earlier window. Group all entries assigned to the same window, regardless of gap length. Render one night span from first start to last end, with gaps hatched. Exclude any portions covered by Nap entries from hatching and WASO. An active entry ends at now for live presentation and is marked ongoing.
- The gap is only time between logged sleeps, not proof of waking: label the metric **WASO logged**, with accessible wording explaining the limitation when details are opened. Do not interpret zero as proof of no wakings or call unobserved time confirmed sleep. Night span is called **night sleep period**, not time in bed. No legend is required.
- Display lighter-coloured naps. Per display-day row, sum Nap intervals clipped to existing sleep-day-start boundaries. Show the night sleep period and WASO for the night whose morning calendar date matches the row's date. Night grouping and metrics are computed across the full underlying entries before clipping to visible chart rows, including at effective-date and history-load boundaries.

## Implementation

1. Inspect existing API, UI, backup/restore and concurrency tests before changing them. Add nullable validated classification override to `sleep_entries` using an idempotent migration, defaulting existing entries to Auto. Preserve it on ordinary edits and stop; allow the edit form to explicitly set or clear it. Update create/edit/active endpoints as appropriate, preserving conflict checks, interval validation and existing client compatibility. Deletion removes associated metadata naturally.
2. Extend sleep settings API and settings UI in `server.js` and `public/index.html` with the mode, effective date and two local times. Validate real calendar dates and HH:MM values server-side; reject equal times and ensure enabling has an effective date. Defaults for existing installations and old backups: mode off, 07:00 wake and 19:00 bedtime. Keep `sleep_day_start` independently editable. Settings saving must not alter sleep intervals.
3. Extend backup export, validation and restore to round-trip settings and overrides, preserving them across device/database restores. Accept legacy backups without the new fields and use defaults. Preserve the existing backup format/version compatibility where possible; inspect restore semantics and ensure omitted legacy fields cannot leave stale classification metadata or settings after replacement. Never include secrets in backups.
4. Add pure helpers adjacent to existing sleep timeline helpers to classify entries, construct local night windows and group nights; use actual timestamp overlap and local calendar arithmetic, not fixed 24-hour assumptions. Compute totals from the same grouped data used for rendering. Apply date gating consistently to timeline, summaries and history while keeping raw individual records accessible for editing/deletion. For a sleep-day row labelled by its `from` local date, apply the new view if that date is on or after the effective date; assign the associated night by morning date independently of the visual bar wrap.
5. Update the timeline to clip night spans, hatching and nap segments to each bar's existing display-day bounds; support spans crossing boundaries and ensure a nap within a night is not obscured. Add the three stats, clear labels and accessible names/details for both colours and hatch, including active sleep. Keep old UI and stats unchanged when mode is off or before the effective date. Add the override control to the existing edit dialog and allow reverting to Auto; individual sleep entries remain inspectable and editable.
6. Handle inconsistent or invalid settings and failed saves visibly; refresh authoritative data on conflicts as the current UI does. Ensure mode and cutoff changes do not destroy persisted overrides, and changing settings immediately recomputes Auto classifications.

## Validation

- Unit tests for majority classification, exact tie, straddling boundaries, long entries, overrides and reset, assignment by overlap/nearest window/tie, and independent day-start changes.
- Group and statistics tests: multiple wakings, arbitrarily long gaps, no inferred wake in a single interval, Nap inside a grouped span, missing nights, active intervals, clipping across rows, effective-date boundary and morning attribution, and no double counting.
- Test DST spring/fall changes and local date arithmetic; verify 23/25-hour display days, windows crossing midnight, and settings applied retroactively.
- API tests for idempotent migration/defaults, validation, concurrent/stale edits, preserving override on start/stop/edit, and unchanged interval/conflict rules.
- Backup tests for new-field round trips and legacy import defaults; regression tests for existing display and logging with mode off. Manually verify timeline interaction, edit/reset, accessibility, light/dark colours and hatch, and settings persistence.
