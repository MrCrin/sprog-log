# PIN Access Gate (server-side PIN + signed cookie)

## Context

Sprog Log is a single-file Express 4 backend (`server.js`) + Postgres (`pg`), serving a no-build React 18 SPA (`public/index.html`, React via unpkg CDN + Babel standalone). Today every `/api/*` route and the static frontend are fully open; README lists "No authentication" as a known limitation. Goal: a basic PIN gate that stops random bots and casual visitors from reading/writing data. Explicitly out of scope: user accounts.

## Decisions (agreed with user)

1. **Server-side PIN with signed session cookie** (chosen over client-side-only gating, hashed-env hardening, and platform basic auth). Enforcement is server-side; the SPA shows a PIN screen client-side.
2. **First-run setup mode instead of env-only config**: if no PIN is configured (fresh deploy or existing deployment upgrading), the server boots in setup mode — all data endpoints stay locked and the UI prompts the first visitor to create a PIN.
3. **PIN stored scrypt-hashed in Postgres** (`app_settings` key/value table, created by the existing `initDb()` bootstrap — no manual migration; existing deployments pick it up automatically).
4. **`APP_PIN` env var = optional override/recovery mechanism.** When set, it takes precedence over the DB PIN for verification and cookie signing. Documented as the lockout-recovery path (also: `DELETE FROM app_settings WHERE key = 'pin_hash'` re-enters setup mode).
5. **30-day persistent cookie** per device.
6. **API-gated only; static files stay public.** The SPA shell contains no secrets (PIN never reaches the client); it renders a setup/unlock screen based on server status. No separate static unlock page.
7. **Zero new npm dependencies** — Node built-in `crypto` (scrypt, HMAC, timingSafeEqual); tiny hand-rolled cookie parser.
8. **Simple in-memory per-IP lockout**: 5 consecutive failed unlocks → 15-minute lockout (HTTP 429). Resets on restart; acceptable for this threat model.
9. **Out of scope**: change-PIN UI, logout/lock button, CSRF tokens (cookie is `httpOnly` + `SameSite=Lax`; cross-origin fetches don't send it), rate-limit persistence, account lockout notifications.

## Data flow

- `GET /api/auth` (always public) → `{ status: 'setup' | 'locked' | 'unlocked' }`
  - `setup`: no DB PIN and no `APP_PIN` env override.
  - `locked`/`unlocked`: PIN configured; determined by validating the request's session cookie.
- `POST /api/setup/pin` `{ pin }` — only succeeds while status is `setup` (else 409). Validates PIN (string, 4–64 chars), stores `scrypt` hash (`salt:hex` format) in `app_settings`, sets session cookie.
- `POST /api/unlock` `{ pin }` — verifies PIN (timing-safe), sets session cookie; 401 on wrong PIN; 429 while IP is locked out; successful unlock resets the failure counter.
- All other `/api/*` routes → 401 `{ error: 'locked' }` unless a valid session cookie is present. While in setup mode they also 401 (with a `setup_required` marker) — no data is ever served before a PIN exists.
- Session cookie: `sprog_session=<expiryMs>.<hmac-sha256>` where the HMAC key is derived from the effective PIN hash (env override or stored DB hash). Changing/overriding the PIN invalidates all existing sessions. Flags: `httpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=30d`, `Secure` only when `req.secure` (works behind proxies via trust proxy setting).

## Implementation tasks

### `server.js`
1. `initDb()`: add `CREATE TABLE IF NOT EXISTS app_settings (key TEXT PRIMARY KEY, value TEXT NOT NULL)`.
2. Add `app.set('trust proxy', 1)` so `req.ip` is the real client behind Render/Railway-style proxies (note in a code comment: spoofable `X-Forwarded-For` can rotate the lockout bucket — acceptable tradeoff vs. all users sharing one proxy-IP bucket).
3. Auth helpers (keep them pure/unit-testable, no `req`/`res`):
   - `getEffectivePinRecord()` — `APP_PIN` env (validated 4–64 chars at boot) wins; else read `pin_hash` from `app_settings`; else `null` (= setup mode).
   - `hashPin(pin)` / `verifyPin(pin, record)` — `crypto.scryptSync` with per-record random salt, `crypto.timingSafeEqual` for comparison.
   - `signSessionCookie()` / `verifySessionCookie(value, record)` — HMAC-SHA256 of expiry timestamp keyed by the effective PIN record; expiry = 30 days.
   - `parseCookies(header)` — minimal cookie header parser.
4. Lockout: `Map<ip, { fails, lockedUntil }>`; increment on failed unlock, reset on success, check before verifying (429 when `lockedUntil > now`).
5. Endpoints, registered BEFORE the gate middleware: `GET /api/auth`, `POST /api/setup/pin`, `POST /api/unlock`.
6. Gate middleware `requireAuth` mounted via `app.use('/api', requireAuth)` after the three exempt routes and before all existing routes — no changes needed to the 9 existing handlers.
7. Startup log line when in setup mode: `No PIN configured — visit / to create one.` Validate `APP_PIN` format at boot (exit with clear error if set but invalid).

### `public/index.html`
8. Add `authStatus` state (`'loading' | 'setup' | 'locked' | 'unlocked'`); on mount call `GET /api/auth` first. Only run the existing 3-endpoint data fetch when `unlocked` (prevents the onboarding modal appearing on a 401).
9. New components styled with the existing Tailwind/dark-mode patterns (reuse the modal/card look):
   - `SetupPinScreen`: create PIN with confirm field (typo protection), calls `POST /api/setup/pin`, on success → `unlocked`.
   - `UnlockPinScreen`: PIN input, inline errors for 401 ("wrong PIN") and 429 ("too many attempts, try again later").
10. Handle 401 from any later fetch (e.g. expired cookie) by flipping `authStatus` back to `'locked'` — at minimum in the initial-load `.catch`.

### Docs/config
11. `.env.example`: add commented optional `APP_PIN=` with a one-line "override/recovery" note.
12. `README.md`: new "PIN access" section (first-run setup flow, env override recovery, DB-row reset alternative); update the "No authentication" known limitation.
13. `CHANGELOG.md`: add entry under `[Unreleased]`; bump `package.json` to `1.3.0` per repo convention.

## Failure modes / risks

- **Setup race**: between deploy and PIN creation, any visitor could set the PIN. Accepted for this threat model; owner reclaims via `APP_PIN` env override or DB row delete. Documented in README.
- **Forgotten PIN** → recovery via `APP_PIN` env override (documented).
- **Lockout bypass** via spoofed `X-Forwarded-For` (trust proxy) — attacker can rotate buckets but still must guess the PIN; global throttling is deliberately avoided to prevent one bot DoS-ing all users behind a shared proxy IP.
- **Mid-session expiry** UX is minimal (back to unlock screen on next 401) — acceptable.

## Validation

- `node --check server.js` (syntax).
- No test framework in repo; keep crypto helpers pure and smoke-test them with `node -e` if desired.
- If a Postgres `DATABASE_URL` is available, run the server and verify with curl; otherwise hand this checklist to the deployer:
  1. `GET /api/auth` → `setup`; `GET /api/measurements` → 401.
  2. `POST /api/setup/pin` `{ "pin": "1234" }` → sets cookie; same endpoint again → 409.
  3. `GET /api/measurements` with cookie → 200; without → 401.
  4. `POST /api/unlock` with wrong PIN ×5 → 429; correct PIN after lockout expiry → 204.
  5. Restart with `APP_PIN=9999` → old DB PIN rejected, `9999` unlocks.
  6. Browser: fresh visit shows PIN screen; after unlock, tracker loads; hard refresh within 30 days stays unlocked.
